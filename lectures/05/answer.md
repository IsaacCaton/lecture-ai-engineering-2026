- 回答モデルは全方式で `gemini-3.1-flash-lite`。

- `--trace` では、全文投入はツール呼び出しなし。ベクトル検索は `search_materials`、Graphは `search_graph` を各1回呼び、どちらも検索語は `LoRA QLoRA 違い` だった。Treeは `browse_tree` を4回呼んだ。指定したノードは `lec02-main → lec02-main-s045 → lec02-main-p051`。
- 今回の質問では、通常のベクトル検索で必要な根拠を確保でき、入力トークン数と生成API推定費用も最小だった。Graphはこの計測では最速だったが、各方式の計測は1回なので、応答時間の優劣を判断するには複数回の比較が必要。

- 取り組んだレベルは「実装」。
- `app/retrieval.py` を変更した。`AIE_RAG_NEIGHBORS=1` のとき、ベクトル検索の上位5件に、各ヒットと同じ資料の前後1ページの本文と引用情報を追加する。資料IDとPDFページ番号の組で照合して、資料の境界と重複を処理した。ベクトル検索の順位を保ち、追加ページの距離は `null` とした。索引は同梱版を使用した。
- 比較質問A「LoRAとQLoRAの違いは何ですか。また、第2回のチャットボット演習では、出力形式と資料固有の知識をそれぞれ何で補いますか？」
- 比較質問B「LoRAとQLoRAの違いは何ですか？」
- 取得処理の事前確認では、第1〜3回の講義資料と同梱DBを使い、第2回PDF p.52の保存済み埋め込みを同じ検索ベクトルとして両方式に入力した。時間は検索・本文追加・ツール出力のJSON化を含む11回の中央値。質問のオンライン埋め込みと回答生成は未計測。

- 質問Aに対応する根拠はp.52とp.53。事前確認では、通常検索でp.52が得られ、拡張時にp.53の本文も取れた。p.53で、演習では出力形式にFT、資料に固有の事実にRAGを使うという説明を確認した。
- 質問Bの違いはp.52で確認できる。拡張時には、質問に直接関係しないp.10のトークン予測やp.12のサンプリングの説明も追加された。隣接する本文が常に回答の根拠になるとは限らない。

### Geminiでの比較

同じ `AIE_MODEL`、同梱DB、同じ質問文で各方式を実行する。各質問の回答と引用、`[tool call]` の検索語と回数、`[time]`、`[usage]`、`[cost]` を記録する。

~~~bash
q_a='LoRAとQLoRAの違いは何ですか。また、第2回のチャットボット演習では、出力形式と資料固有の知識をそれぞれ何で補いますか？'
q_b='LoRAとQLoRAの違いは何ですか？'
for question in "$q_a" "$q_b"; do
    AIE_RAG_NEIGHBORS=0 uv run python -m app.agent --trace "$question"
    AIE_RAG_NEIGHBORS=1 uv run python -m app.agent --trace "$question"
done
~~~

回答モデルは全4回で `gemini-3.1-flash-lite` を使用した。検索対象は同梱DBの第1〜3回。モデル応答回数はどの実行も2回だった。Ubuntuで既存テスト17件が通過した。

- 質問Aでは、通常版も2回目の検索でp.53を取得し、FTとRAGの使い分けを説明できた。保存済みベクトルを使った事前確認ではp.53を補えたが、実際のエージェントは検索語を変えて不足する根拠を探せることが分かった。
- 質問Bでは、同じ検索語で両方式がp.51、52を引用した。前後ページ付きでは、入力が2,240トークン増え、回答完了までの時間も1.22秒延びた。
- 各条件の計測は1回で、質問Aでは2回目の検索語にも違いがあった。今回の結果を踏まえると、通常検索で必要な根拠を取れなかった場合に前後ページを追加する方法を試したい。
